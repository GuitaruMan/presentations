# 2028 과목 선택 안내 — 데이터베이스 이원화 설계

- 대상: `ForWeb/work/교육과정/2028과목선택/`
- 목적: 조회·선택 화면(웹, 추후 앱)과 과목·교육과정 데이터를 분리해, 매년 대학 권장과목·학교 교육과정이 바뀌어도 유지보수가 쉽게 한다. 이 작업(1번)이 끝나야 안드로이드/iOS 앱(2번)을 만들 수 있다.

## 배경 — 현재 구조

정적 GitHub Pages 배포. `app.js`가 `data/*.json` 8개 파일을 fetch해서 렌더링한다.

- `recommendations.json` (576KB) — 대학별 권장과목·조건. PDF/엑셀을 `Create/ForCir_data/build_*.py` 빌더로 읽어 생성.
- `subject_master.json` — 과목 마스터(교과군·유형·설명).
- `cohorts.json` — 입학연도별 코호트 설정(2025-g3, 2026-g2 등), 각 코호트가 어느 편성표/폐강 파일을 쓰는지 지정.
- `school-2025.json`, `school-2026.json` — 코호트별 개설과목 표 + `meta`(이수규칙·선수과목·선택슬롯·유의사항).
- `closed-2025.json`, `closed-2026.json`, `closed-2026-g3.json` — 코호트별 개설현황(폐강). `admin.html`이 GitHub API로 직접 커밋.
- `help_content.json` — 학생용 설명서 문서.

역할은 실질적으로 두 명이 아니라 **사용자 본인 한 명**이 개발자 겸 유일한 관리자(담당 부장 교사)를 겸한다. 학생은 로그인 없는 조회 전용 사용자다.

## 결정된 방향

1. **DB**: Supabase(PostgreSQL)로 전환. 무료 티어로 시작.
2. **대학 권장과목**: 계속 AI(Claude)가 PDF/엑셀 원본을 읽어 빌더 스크립트로 처리 — 대학마다 조건 표현이 제각각이라 자동 폼보다 사람(AI)이 원문을 판단하는 편이 낫다는 기존 결론 유지. 빌더의 마지막 출력 단계만 "JSON 파일 저장" → "Supabase upsert"로 바꾼다.
3. **학교 교육과정(개설과목 + 이수규칙)**: 두 경로 병행.
   - AI 경로: 지금처럼 자연어로 요청하면 Claude가 DB에 직접 반영.
   - 폼 경로: `admin.html`에 신설할 입력 폼에서 직접 편집.
   둘 다 같은 DB를 향하므로 충돌 없이 병행 가능. 폼이 다루지 못하는 새 규칙 유형이 생기면 우선 AI 경로로 처리하고, 자주 쓸 것 같으면 폼에 섹션을 추가한다 — 폼은 완성 후 고정이 아니라 계속 확장되는 도구.
4. **개설현황(폐강)**: 기존처럼 `admin.html`에서 직접 편집하되, 저장 대상만 GitHub 커밋에서 Supabase 쓰기로 바꾼다.
5. **학생 조회(웹·앱 공통)**: Supabase를 anon key로 직접 읽기. 로그인 없음. 학생 개인 선택(내 과목 담기 등)은 서버에 저장하지 않고 지금처럼 기기 로컬(localStorage)에만 남긴다.
6. **인증**: 관리자 1명(사용자 본인)만 로그인하면 되므로, Supabase 이메일+비밀번호 로그인으로 충분. 회원가입 기능 불필요 — Supabase 대시보드에서 계정 1개만 미리 만들어 둔다.

## 아키텍처

```
[PDF/엑셀 원본]
      │  (기존 build_*.py 그대로, AI가 원문 판독)
      ▼
[Python 빌더] ──upsert──▶ [Supabase(PostgreSQL)]
                                   │
                    ┌──────────────┼──────────────┐
                    │              │              │
              (읽기, anon key)  (쓰기, 관리자 로그인)
                    │              │
             [학생 웹/앱]      [admin.html]
          (조회 전용, 로그인 없음)   (관리자 1명,
                                   개설현황 + 학교
                                   교육과정 폼 편집)
```

## DB 스키마

설계 원칙: 지금 JSON의 "조건"(택N, 교과군)처럼 대학·학교마다 모양이 들쭉날쭉한 값은 `jsonb` 컬럼에 그대로 두고, 검색·필터링이 필요한 값(교과군, 학년, 계열 등)만 진짜 컬럼으로 둔다. 지금 빌더가 만드는 JSON 구조를 거의 그대로 옮길 수 있어 마이그레이션 비용이 적다. **현재 데이터 구조 자체는 바뀌지 않는다 — 값이 파일에서 DB로 옮겨질 뿐이다.**

```
subjects (과목 마스터)
  id, name, 교과군, 유형, 별칭 jsonb, 설명, 출처쪽

universities (대학)
  id, 이름, 출처, 발표일, 제시범위, 제시강도, 강도근거, 안내 jsonb

admission_units (모집단위)
  id, university_id → universities, 계열, 단과대학, 이름,
  핵심 jsonb, 권장 jsonb, 조건 jsonb, 비고, 권역, 지역

school_cohorts (코호트: 2025-g3, 2026-g2 등)
  id, 코호트id, 입학연도, 대상, 제목, 설명, 선택군 jsonb, 노출

school_offerings (학교 개설과목 — 코호트별 106개 행)
  id, cohort_id → school_cohorts, 과목, 교과군, 유형,
  운영학점, 선택군, 학년, 학기 jsonb, 평가

school_rules (코호트별 이수규칙·선수과목·선택슬롯 — meta 전체)
  id, cohort_id → school_cohorts, 이수규칙 jsonb, 선수과목 jsonb,
  선택슬롯 jsonb, 유의사항 jsonb, 과정구분 jsonb

closed_subjects (개설현황/폐강 — 코호트별)
  id, cohort_id → school_cohorts, 과목, 학기, 사유, 갱신일
```

`help_content.json`(설명서)은 관계형으로 쪼갤 실익이 없어 단일 jsonb 테이블 또는 기존 정적 파일 그대로 유지해도 무방하다 — 자주 바뀌지 않는 문서이기 때문.

## admin.html 학교 교육과정 폼

두 개 탭으로 구성. (브레인스토밍 중 시각적 목업으로 확인·승인됨)

**탭 1 — 개설과목**
- 표 형태 CRUD: 과목명, 교과군, 유형, 운영학점, 학년, 선택군, 평가방식.
- 검색으로 106개 중 찾기, 행 추가/삭제, 셀 직접 수정.
- 여기서 어떤 과목을 "선택군2"로 지정하면, 그 과목이 이수규칙 탭의 "선택군2 택N" 후보군이 된다.

**탭 2 — 이수규칙 빌더**
1. **선택슬롯** — "택N"의 N을 정하는 곳. 선택군별로 학년, 1학기 택N, 2학기 택N을 입력. (과목 후보 자체는 탭 1에서 정해짐 — 두 화면이 "몇 개를 고르는지"와 "무엇이 후보인지"를 나눠 맡는다.)
2. **교과군 최소 이수** — 교과군 선택 + 최소 과목 수, 행 추가/삭제.
3. **교과군 최대 이수** — 교과군 다중 선택(칩 UI) + 합계 최대 과목 수.
4. **과학중점 전용 규칙** — 과제연구 필수 과목, 일반선택 필수 과목(다중 선택), 진로선택 심화 최소, 수학 최소.
5. **선수과목 관계** — "과목 A ← 먼저 들어야 하는 과목 B" 쌍을 추가/삭제.

이 5개 섹션이 지금 `school-*.json`의 `meta.이수규칙`/`meta.선수과목`/`meta.선택슬롯`을 대체한다. 새로운 규칙 유형이 생기면 먼저 AI 경로로 DB에 반영하고, 자주 쓰일 것 같으면 이후 폼에 섹션을 추가한다.

## 마이그레이션 순서

1. Supabase 프로젝트 생성, 위 스키마(7개 테이블)로 DB 구축.
2. 기존 JSON 8개를 한 번에 적재하는 이관 스크립트 작성 → 실행.
3. `app.js`의 `fetch('data/*.json')`을 Supabase 호출로 교체(화면 로직은 그대로, 데이터 소스만 교체).
4. `admin.html`의 개설현황 기능을 GitHub 커밋 방식에서 Supabase 쓰기로 교체.
5. `admin.html`에 학교 교육과정 폼(개설과목 표 + 이수규칙 빌더) 신규 추가.
6. 기존 `build_*.py` 빌더들의 마지막 저장 단계만 "JSON 파일 쓰기" → "Supabase upsert"로 교체.
7. 웹이 안정되면 기존 정적 JSON 파일 정리(백업 후 삭제 또는 보관).

각 단계마다 실제로 확인하며 진행하고, 문제가 생기면 이전 단계로 되돌릴 수 있게 순서대로 진행한다.

## 범위 밖 (이번 설계에서 다루지 않음)

- 안드로이드/iOS 앱 자체의 구현 방식(PWA 포장 vs 네이티브)은 아직 미정 — 1번(DB 이원화) 완료 후 별도로 결정.
- 학생 로그인·서버 측 개인화 저장 — 필요 없음(로컬 저장 유지)으로 확정, 향후 요구 시 재논의.
